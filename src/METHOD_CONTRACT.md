# Paper Runner Method Contract

This document is the method-as-described ledger for `src/`. It names what each
experiment in the paper runner is supposed to measure, along four axes the previous
audit flagged:

- **Per-example conditioning** — does the LM actually see an input-dependent LoRA at
  the point where loss is computed and at the point where the metric is read?
- **Gradient flow** — does the training loss backpropagate into the bridge/prefix
  parameters the paper claims are being trained?
- **Baseline matching** — is each baseline the fair version of the thing it is meant
  to be compared against (same capacity budget, same signal pathway, same eval pass)?
- **Encoder provenance** — is every feature extractor loaded from a known, versioned
  checkpoint the paper cites, and not a fresh init?

The contract is written against the rendered manuscript `arxiv/main.tex`
(generated by `src/render_arxiv.py`; the markdown draft in the repo root is
historical).
It is purely a specification — no code is changed by this document. The
historical discrepancy review (§2 and §3 in earlier drafts) and the audit
findings it tracked have been removed; that progression lives in git history.

## 1. Experiments and what they must measure

### 1.1 `run_static_lora` — static LoRA baseline (Table, Section 5.1)

**Claim.** A text-only LoRA baseline with no sensor signal, used to separate "extra
trainable capacity" from "sensor conditioning."

**Must satisfy:**

- Per-example conditioning: **not required**. This baseline has no conditioning signal
  by design. But the LoRA weights that are used at eval time must be the weights that
  were actually trained, i.e. `self.lora_a` / `self.lora_b`, with no stale `_hyper_*`
  attributes shadowing them.
- Gradient flow: the text-only cross-entropy loss must produce nonzero gradients on
  every parameter in `get_lora_params(model)`. Nothing else should train.
- Baseline matching: same base checkpoint, same tokenizer, same val loader, same
  eval token budget as the bridge runs. Same LoRA rank and target ("all"). Same
  optimizer recipe as the bridge runs: AdamW, weight decay 0.01, grad clip 1.0,
  mean loss over the batch.
- Encoder provenance: n/a (no encoder).

**Sanity checks that would prove it:**

1. After one `loss.backward()`, every tensor in `get_lora_params(model)` has
   `grad is not None` and `grad.norm() > 0`.
2. No LoRA module has `_hyper_a` or `_hyper_b` set at any point during this run.
3. Eval BPB equals a second eval call right after training (no stale state leaking
   across calls).

### 1.2 `run_bridge_experiment(feature_mode="true")` — conditional bridge

**Claim (Sections 3, 5.1).** A hypernetwork observes sensor features and generates a
LoRA weight vector injected into the frozen LM. Improvements over static LoRA are
attributed to input-dependent conditioning.

**Must satisfy:**

- Per-example conditioning: at every training step, the LM forward pass used to
  compute the BPB loss must see **a LoRA that was generated from the sensor input
  associated with that same forward pass**. A pooled/batch-mean LoRA applied to the
  entire batch violates this — the LM is then being conditioned on "the average
  sensor in this batch," not on any specific input. If text and sensor batches are
  sampled independently (as is the case here), then at a minimum each text example
  should see its own sensor-derived LoRA, and the pairing should be per-example.
- Per-example conditioning also applies at **eval time**: the BPB value reported in
  the paper must be measured with a LoRA that reflects the trained bridge's actual
  input-to-weight function, not an arbitrary LoRA snapshot left over from the last
  training step.
- Gradient flow: the bridge's `.mlp` and `.proj` parameters must receive gradient
  from both (a) the LM text loss through `_hyper_a`/`_hyper_b`, and (b) when
  `diversity_weight > 0`, from the diversity loss on `per_sample_weights`.
- Baseline matching: same base LM, same LoRA rank/target, same eval tokens, same
  fixed training step count as the static LoRA baseline (step counts, not
  wall-clock, so optimization amount is hardware-independent). The only thing that
  should differ is whether LoRA weights are generated from sensor features or
  trained as raw parameters.
- Encoder provenance: the sensor feature extractor must be loaded from the
  checkpoint the paper names (MobileNetV3 + trained PerceiverResampler for vision;
  ESC-50 encoder for audio; UCI-HAR encoder for IMU), with `strict=True` state dict
  loading so a checkpoint schema mismatch fails loudly.

**Sanity checks that would prove it:**

1. Bridge parameters have nonzero gradients after `loss.backward()` in every step,
   with both diversity-on and diversity-off.
2. In any batch, `bridge(features)` with non-identical features produces LoRA vectors
   with pairwise cosine similarity < 0.999 (no mode collapse at init).
3. At eval time, the LoRA actually being applied is generated fresh from sensor
   features (not a left-over training artifact).
4. Removing the sensor signal (feature mode "random") at the same budget produces
   measurably different final BPB from feature mode "true" — otherwise the
   conditioning claim is empty.

### 1.3 `run_bridge_experiment(feature_mode="shuffled" | "random" | "constant")` — controls

**Claim (Section on feature controls).** The controls preserve trainable capacity
while degrading or removing the per-input feature signal. IMPORTANT INTERPRETATION
LIMIT: in the BPB pipeline, text batches and sensor indices are sampled
independently, so there is no semantic sensor↔text alignment for "shuffled" to
destroy — "shuffled" is distributionally identical to "true" there and serves as a
seed-noise sanity control only. The semantically meaningful shuffled control lives
in `run_task_eval`, where features are label-paired. The paper text must not claim
the BPB true-vs-shuffled gap measures conditioning.

**Must satisfy:**

- All sanity requirements of 1.2 apply.
- The only difference between "true", "shuffled", "random", and "constant" runs is
  the feature selection inside `_bridge_features_for_indices` — everything else
  (bridge architecture, optimizer, schedule, eval pass) must be byte-identical.
- "shuffled" maps sensor indices through a fixed run-global derangement
  (`_make_global_shuffle_map`: a permutation with no fixed points), in both
  training and eval.
- "random" must draw a fresh `randn` every step, not a fixed noise vector.
- "constant" must feed the same fixed feature vector (the bundle-mean feature,
  computed once) on every step and at eval — the capacity-matched control that
  isolates "extra trainable parameters" from any per-step stochastic signal.

**Sanity checks:**

1. `_make_global_shuffle_map` returns a valid permutation with zero fixed points.
2. `_bridge_features_for_indices(..., "random")` produces a different tensor on
   every call; `(..., "constant")` produces an identical tensor on every call.
3. Trained bridges under "constant" recover BPB improvements close to the static
   LoRA baseline (the capacity floor); "random" measures stochastic-conditioning
   regularization above or below that floor.

### 1.4 `run_bridge_experiment(diversity_weight>0)` — diversity sweep (Section 6.1)

**Claim (Section 6.1).** Without regularization, the bridge collapses to a single
LoRA regardless of input. A contrastive loss on per-sample weights produces
structured, input-dependent adaptation.

**Must satisfy:**

- Diversity loss is computed on **per-sample** bridge outputs with full gradient
  flow to the bridge parameters. It cannot be computed under `torch.no_grad()` or
  on features that were detached upstream from the bridge parameters.
- Per-example conditioning (as in 1.2) must hold so that "diversity between
  per-sample LoRAs" and "what the LM actually sees" are the same thing. If the LM
  only ever sees pooled LoRA, then the reported cross-input cosine similarities and
  the reported BPB improvements do not describe the same object.
- The sweep must vary **only** `diversity_weight` between runs. Seeds, schedules,
  data order, and encoder state must match.
- At λ=0, mode collapse (cosine similarity → ~1) is expected. At λ>0, collapse must
  be resolved. The paper's Table in 6.1 takes this for granted.

**Training-side verification surface:**

- `result.last_diversity` is the final-step training loss-side diversity signal.
- `result.diversity_weight` records the λ used for that run.
- `result.improvement` is the LM-side BPB delta for the same trained bridge.

**Held-out probe verification surface:**

- `result.heldout_probe.cross_input_cosine_mean` is the primary collapse metric for
  Section 6.1.
- `result.heldout_probe.paper_pairs` contains the named centroid-pair cosine values
  cited in the paper text.
- `result.heldout_probe.within_activity_cosine_mean` is the per-activity consistency
  check for same-label LoRA structure.
- `result.heldout_probe.activity_counts` confirms how many held-out test examples
  contributed to each activity-level probe statistic.

**Sanity checks:**

1. After `loss.backward()`, `bridge.mlp[-1].weight.grad.norm() > 0` at every λ.
2. At λ=0, `result.heldout_probe.cross_input_cosine_mean` is > 0.99 (collapse); at
   λ=0.1, it is < 0.5.
3. At each λ, the per-sample LoRA vectors used to compute the diversity loss are the
   same vectors the LM was conditioned on — not a pair of disjoint computations.
4. `result.heldout_probe.paper_pairs` shows motion-vs-still centroid cosines that
   are materially lower than same-family motion pairs once λ>0 resolves collapse.

### 1.5 `run_composition` — conditioned additive merge (Section 5.3)

**Claim (Section 5.3).** Train independent bridges for each modality, then at eval
merge per-example per-brick LoRA vectors by averaging across bricks. The merged LoRA
is per-evaluation-example, mirroring the per-example bridge eval (§1.2). The default
eval mode is `conditioned`. A `fixed` mode (single batch-mean LoRA per brick, single
merged LoRA used for the entire eval pass) is retained as an opt-in for legacy
comparison only — paper-facing numbers come from the `conditioned` mode unless
explicitly stated otherwise.

**Must satisfy (`conditioned` mode, default):**

- Each per-brick run must be a valid conditional bridge per §1.2 — per-example LoRA
  injection during both training and eval, fresh sensor-conditioned LoRA at the
  point where the metric is read.
- For each val example, every active brick produces a per-example LoRA from its own
  sensor stream. Per-brick sensor batches are walked deterministically via cycle
  indices so the composition result is reproducible given the same trained bridges.
- The per-brick LoRA vectors are stacked along a new dimension and averaged
  elementwise across bricks to produce one merged LoRA per val example.
- That merged LoRA is applied via `apply_hypernet_weights` immediately before the
  corresponding val example's forward pass, with no subsequent
  `apply_hypernet_weights` call overwriting it before the example's loss is read.
- The base LM that the merged LoRA is applied to must be a **fresh** load of the
  same checkpoint, with `apply_lora` called once, and no stale `_hyper_*` from any
  of the per-brick training runs.

**Must satisfy (`fixed` mode, opt-in only):**

- Each brick's contribution is one fixed LoRA computed once before eval, by mean-
  pooling per-sample bridge outputs over a deterministic sensor sample (first-N via
  cycle indices, not random draw, for reproducibility).
- The merged LoRA is the elementwise mean across per-brick fixed LoRAs and is
  applied exactly once before the eval pass; it is not refreshed per example.
- Same fresh-load and no-stale-`_hyper_*` requirements as the conditioned mode.
- Numbers from this mode must be labeled as such in any results / paper text. They
  are not interchangeable with `conditioned` numbers.

**Sanity checks:**

1. (Conditioned) For two distinct val examples in the same eval batch, the merged
   LoRA applied differs (the per-brick per-example vectors are not all equal).
2. (Conditioned) A single-brick composition run **at the same step count as the
   benchmark bridge** reproduces that bridge's BPB to within seed noise — the
   merged LoRA collapses to that brick's per-example LoRA when there is only one
   brick to average. (Default suite trains composition bricks for 150 steps vs the
   benchmark's 300, so Table 1 and the composition table are not directly
   comparable; the paper must say so.)
3. (Fixed) Applying the merged LoRA and immediately re-applying the same merged
   LoRA gives identical BPB (no hidden state leak).
4. Both modes: changing the per-brick training seed changes the composition result
   in the expected direction; eval-time sensor cycle ordering does not affect the
   final number beyond a deterministic permutation of which val example sees which
   sensor index.

### 1.6 `run_prefix_experiment` — prefix-tuning baseline (Section 5.1)

**Claim (Section 5.1).** Prefix tuning is a matched embedding-space baseline. It
fails catastrophically on frozen small LMs, which is evidence that weight-space
conditioning is the viable path.

**Must satisfy:**

- Per-example conditioning **must be honored** in the prefix baseline too. If the
  prefix is per-example for the bridge method, it must be per-example for the
  prefix baseline. The audit's Finding 4 was that the old prefix runner averaged
  per-example prefixes into a single global prefix; that makes the baseline
  artificially weak.
- Gradient flow: only `prefix_proj` parameters should train. The LM must be fully
  frozen (including any previously-applied LoRA, which should not be applied here).
- Baseline matching: same base LM, same eval passes, same number of transformer
  context positions (the prefix occupies `n_prefix` of the 128 positions, so the
  prefix condition sees proportionally fewer text tokens per row — inherent to the
  method; the eval packs the val stream into shorter rows for the same reason, and
  both effects must be disclosed in the paper rather than hidden). Same precision
  context (autocast) for training and eval as every other condition. The trainable
  parameter budget should be documented even if it's larger than LoRA — prefix
  tuning with comparable capacity is the honest comparison.
- Objective alignment: the dataloader yields pre-shifted targets (`y = row[1:]`),
  so with `n_prefix` prefix tokens the logit slice paired with `ty` must be
  `logits[:, n_prefix:]` — predicting exactly one token ahead, in both the training
  loss and the eval loss. (A previous version sliced `logits[:, n_prefix:-1]`
  against `ty[:, 1:]`, silently training a two-tokens-ahead objective.)
- Metric units: the prefix eval must report byte-weighted bits-per-byte computed
  exactly like `evaluate_bpb` (per-position losses weighted by `token_bytes[vy]`
  with the `nbytes > 0` mask), never raw bits-per-token, so `improvement =
  baseline − final` compares like units.
- Encoder provenance: same encoders as the bridge method, loaded from the same
  checkpoints.

**Sanity checks:**

1. For a batch of 8 distinct sensors, `prefix_proj(features)` produces 8 distinct
   prefix tensors (pairwise L2 distance > 0 between all pairs).
2. At eval time, each text example is scored with a prefix generated from some sensor
   feature, not a single global average.
3. `prefix_proj` parameters have nonzero gradients; no LM parameter has a gradient.
4. With an untrained near-zero prefix projection, the prefix eval BPB lands near
   the no-prefix baseline (gross divergence indicates an alignment or unit bug,
   not a method failure).

### 1.7 `run_task_eval` — task-aligned ranking metrics (Table 7)

**Claim (Section 5.2, Table 7).** Task-level evaluation on IMU activity ranking and
ESC-50 audio category ranking. Reports top-1, top-2, and average rank, under
"true", "shuffled", "random", and "no_bridge" conditions.

**Must satisfy:**

- Per-example conditioning is **mandatory** here. Each test sensor must produce its
  own LoRA, and all category labels must be scored against the LM conditioned on
  that same LoRA. This is the heart of the claim.
- Gradient flow: during the (brief) training phase, bridge parameters must receive
  gradient from the per-example loss accumulation. Overwriting `_hyper_a` between
  per-example forwards must not break the autograd graph for earlier examples (it
  doesn't, because each forward captures its own reference).
- Baseline matching: all four conditions share the same model reload, the same
  LoRA application, the same training budget, and the same test subset.
  `no_bridge` must genuinely apply a zero LoRA so that it is measuring "LoRA
  capacity added but no signal injected," not "no LoRA wrapper at all."
- Encoder provenance: the classification encoders used to compute features must be
  the same checkpoints named in the paper, and the train/test split on the sensor
  data must not leak between encoder pretraining and this task eval (the paper
  doesn't discuss this, but it matters for the numbers to mean anything).
- Metric provenance: `rank1`, `top2`, and `avg_rank` must be computed inside this
  script. The audit's Finding 6 was that the previous runner did not compute top-2
  or avg rank at all — the rewrite must compute them directly from the per-example
  scoring loop.
- Label tokenization: every category must be scored on the **natural tokenization
  of `prompt_template + label`** — `_split_label_ids` takes the longest common
  prefix with the standalone prompt tokenization and scores everything after it.
  No category may receive an empty label-token list (which would score −inf).
  (A previous version sliced by `len(prompt_ids)`, which silently dropped the first
  label token — or all of them — whenever the template's trailing space merged
  into the label's first token.)
- Eval subset: the test subset must be label-stratified and seed-shuffled
  (`_stratified_subset`), never a positional truncation of an ordered test file.
  Every category present in the test set must be represented when
  `max_eval_items ≥ |categories|`.

**Sanity checks:**

1. For any two distinct test sensors, the `weight_vector` returned by the bridge
   differs (pairwise cosine < 1).
2. `no_bridge` gives rank1 ≥ 1/|categories| (chance) and the LoRA values all zero.
3. The per-sample scoring loop computes `label_rank = ordered.index(true_label) + 1`
   and updates top-1/top-2/avg-rank from it — no metric comes from an external file.
4. Every scored category has a finite score (no −inf from empty label ids), and the
   eval subset covers all categories with roughly equal counts.

### 1.8 `reproduce.py --suite repro` — reproducibility table (Section 5.4)

**Claim (Section 5.4).** Each bridge experiment is run 3× with seeds 42, 1042, 2042,
and mean ± std is reported. This measures run-to-run stability **of the exact same
experiment shown in Section 5.1**, not a different experiment.

**Must satisfy:**

- The repro job invokes the **identical** code path as the benchmark job. Same
  function (`run_bridge_experiment`), same arguments except seed.
- Eval token budget, sensor limit, training step count, rank, and target all match
  the benchmark suite exactly. The audit's Finding 5 was that the prior
  reproducibility numbers came from a different experimental configuration — the
  rewrite must not do this.
- Mean/std are reported on the `improvement` field (baseline − final), per modality.
- The paper text (5.4) and the JSON output of the repro job must agree on which
  numbers belong to which modality.

**Sanity checks:**

1. Running the benchmark job and the repro job (one seed, same seed) produces
   identical `improvement` to 4 decimal places. With fixed step counts this is now
   a hard requirement, not aspirational — wall-clock budgets made it unachievable
   by construction.
2. The repro summary block lists the exact same `train_steps`, `eval_tokens`,
   `sensor_limit`, `rank`, `target`, and `checkpoint` as the benchmark block.
